## 二、根因（对应 step-inflation 分析的 B/C 层，另有新增）

### B 层：上下文构建（主因）
本 run 每步 input 约 17K tokens，其中真正指令只有一行「那执行 1→2→3→4（P1）」；其余全是历史材料：
- 两份「历史上下文」user 消息：一份嵌入 **Calculator.kt 全文 261 行**、一份嵌入 **CalculatorReducer.kt 全文 169 行**（带行号的读文件摘录被整体注入）；
- Memory Snapshot + Reflections Snapshot 两块 Dynamic Context 长文本。
模型每步都在被淹没的上下文中**从头重建任务认知**——这是开场白四连的直接机制：每次重建产出的结论相同（「先读源码确认」），动作也相同（重复读），因为真正该做的改动埋在一堆历史文件全文里无法稳定定位。

### C 层：压缩摘要的指代消解失败（新增观察点）
- 指令「1→2→3→4」依赖上一轮对话内容，而上一轮已被 compact；摘要里写的是 `Latest message: "那执行 1→2→3→4（P1）" — execute the pending P1 items (copy entry → deliver features)`——把指代消解成了**另一种解读**（copy-result 交付），与模型自己的解读（README/循环小数/指数/输入四项）互相矛盾；
- 一个指令在上下文里同时存在两种互相矛盾的解读 → 模型每步重述确认（死循环）、最终倒向摘要里的解读（漂移）。**compactor 对指代式指令（“1→2→3→4”）没有做消解或标注「消解不确定」，直接把猜解放进摘要**，这是本次混乱的结构性诱因。

### A 层：模型能力（放大器）
- v4-flash 在 17K 长上下文 + 矛盾解读下 reasoning 空转：54–61 秒产出 7–8.7K tokens 的思考却只有一句开场白——「想得多、动得少、重复动」；
- 数字幻觉（31 项/20-23）也是 flash 在长上下文里常见的行为退化。与 3.2 待办（flash→更强模型）的判断完全一致，且本案例补了一条新证据：**幻觉数字会进入开场白并被逐字复述四遍**。

## 三、数字幻觉的直接扳机（2026-09-03 复查补证）

**「31 项、编号 20-23」不是模型自发脑补，是 R3 跨会话清单检索的错误命中喂出来的。**

实测 `detect_list_reference`（`cross_session_retrieval.py:47-51` `_NUMBER_REFERENCE`）：

| 消息 | 提取结果 |
|---|---|
| `那执行 1→2→3→4（P1）` | **`1`**（箭头截断） |
| `做 1、2、3、5` | `1、2、3、5`（正确） |
| `执行 1-2-3` | **`1`**（连字符截断） |
| `执行 1~4` | **`1`**（波浪号截断） |

分隔符词集只有 `[、，,\s]`，不含 `→ - ~ 至` 等常用列表分隔符。数字串在「1」处截断 → R3 按 number=1 检索 → 命中清单第 1 条「**沙箱 git 仍不可用**」（一条阻塞状态记录，非任务项）→ 以「历史上下文（非当前任务）：此前会话曾产出清单『app 有哪些需要优化的？』，条目：1. 沙箱 git 仍不可用…」注入。

于是模型窗口里同时存在三份互相矛盾的「清单」描述：①R3 注入的「条目 1 = git 不可用」②compact 摘要的「16-item / copy entry → deliver features」③用户指令「1→2→3→4（P1）」本意四项。模型无法对齐 → 脑补「31 项、编号 20-23」（幻觉数字）→ 每步重述确认（死循环）→ 最终倒向 R3 注入与摘要里共同的「git 阻塞」主题（漂移去核验 git）。**错误注入违反了 R3 自身的 no-op 设计哲学**（miss 是严格 no-op，错误命中却照常注入）。
