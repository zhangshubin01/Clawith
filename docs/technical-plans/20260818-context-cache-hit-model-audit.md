## 1. 命中模型问题清单

### V1【硬上限】「历史严格 append」与平台两处既有滑动窗口机制冲突

方案配套 ② 要求「历史严格 append、不重排不摘要」，但平台上存在两个**已实现**的滑动窗口，一旦触发即每轮从头裁剪历史：

1. **Session 快照**（`session_context_service.py`）：`recent_session_messages_snapshot` = 最近 N 条用户可见消息（`AGENT_RUNTIME_SESSION_RECENT_MESSAGES` 默认 **20**，`config.py:172`），取数带 `LIMIT`（`_recent_messages_statement`）。窗口满员后每新增一条即从头部滑出一条 → 该段历史不再是 append-only，前缀在窗口头部断裂。缓解：该快照在 run 内来自 checkpoint（`context_builder.py:507-521`），单 run 内基本冻结，滑动发生在 run 边界；跨 run 历史本就不同，损失有限——但**同 session 多 run 共享前缀**场景会受影响。
2. **Thread 消息**（`context_builder.py:540-546` → `tool_exchange.py:836-854`）：`build_recent_tool_safe_window(thread_messages, token_budget=run_message_token_budget, ...)`。当 thread 历史超过预算时**从头裁剪**，被裁掉的部分生成 `omitted_tool_exchanges` 摘要注入 runtime JSON（`model_step_service.py:546-550`，摘要落在动态块内，这点无害），但裁剪点每轮前移 → thread 历史前缀每轮断裂，共同前缀检测只能保住 S+Tools，**历史命中归零，回到现状**。

现网「33k + 每轮 +1k 线性涨」恰好证明该 run 尚未触及预算（裁剪未启动），方案收益成立；但**收益只存在于「未裁剪区间」**。一旦历史涨到预算/窗口上限，方案收益归零。这不只是风险：与 L4（历史压缩阈值化）天然互斥（OpenAI 201 §4.6 已警告压缩破坏缓存）。修正后的收益表述见 §4。

### V2【必须修】system 仍有两条非静态路径

1. `model_step_service.py:1343-1349`：`requires_confirmation` 分支把 `# Group Confirmation Required...` **拼进 static_prompt 尾部** → 该轮 system 字节流变化 → 从 token 0 起所有前缀单元（含 S+Tools 11.6k）全灭，下一轮才重建。触发条件 = 工具确认态（group 场景）。方案配套 ① 只处理了 `runtime_instruction`，**漏掉了这条**。应把这段文案同样并入末尾动态块。
2. `client.py:251-252`：`to_openai_format` 把 `dynamic_content` 拼进 **system content**。`normalize_provider_messages`（`client.py:391-427`）注释自称「折入 uncached dynamic tail」，但实际序列化位置是 system 消息尾部——它在 token 流中位于 tools 和全部历史**之前**。只要 `runtime_instruction` 非空，断点在 system 内部，tools 都跟着 miss（现网 11.6k 恒命中反证现网 runtime_instruction 恒空）。方案配套 ① 方向正确，落地后必须保证 `dynamic_content` 恒为 None。

### V3【不变量】动态块必须是消息序列最后一条，且永不入库

- `_prompt_messages` 的 `deferred_current`/`input_content`/`directive` 追加逻辑（`model_step_service.py:701-724`）都在动态块之前，重排后动态块要排到它们**之后**；任何未来代码路径在动态块后再补消息（新注入逻辑、新 provider 适配）都会直接毁掉整个方案。建议用构造顺序断言测试固化。
- 动态块是 `_prompt_messages` 合成消息、不入库（现网行为）——这条必须写进缓存回归检查表成为不变量：若未来把动态快照持久化进 session/thread，下一轮它会以「历史」身份回放且内容已变 → 前缀断裂。

### V4【审计清单】历史逐字节稳定的隐患点

- **截图证据注入**（`model_step_service.py:1379-1458`）：screenshot tool 消息在请求时被替换为 base64 data URL（`compress_bytes_to_base64`）。同一 ref → 同一 bytes 时编码确定，前缀稳定；但任何压缩参数/库版本变化都会使该历史消息内容变化 → 断裂点。建议加「重放两轮字节级一致」回归测试。
- `_model_message_content` 对 dict content 用 `json.dumps(ensure_ascii=False)` 无 `sort_keys`（`model_step_service.py:573-576`）——键序取决于存储字节序；存储端若出现同义 JSON 键序不一致，会破前缀。低概率，属测试覆盖项。
- `model_visible_thread_messages`（`thread_visibility.py`）的 current_start 过滤：thread 只追加时被过滤集合是稳定前缀 → 安全；但旧消息事后被编辑（补 tool_calls / 改 runtime_intent）会改变可见集合 → 断裂。
- DB 取数排序已确定性（`created_at asc, id asc`，`session_context_service.py:366/470/499/533`）✓，与 L1 修 tools 排序同类问题，历史侧无需再改。

### V5【跨层冲突】工具集任何变动 = 全局缓存重置；L3-B 与缓存根本互斥

- 所有缓存单元都是从 token 0 起算的前缀单元 → **tools 字节流一变化，S+Tools 单元和历史单元全部失效**（不只是 tools 自身那 9.5k）。L2（改 schema 描述）、L3-A（换工具子集）每次上线都会重置所有在跑会话的缓存一次——一次性成本、可接受，但发布节奏需知晓（与 L2「一次性成本可忽略」的判断一致）。
- **L3-B（每轮动态注入工具索引）与 DeepSeek 前缀缓存根本冲突**：每轮 tools 字节流都变 → 每轮从 tools 处全 miss。方案文档 L3-B 必须标注「仅当每轮 tools 变化被放弃、或改成会话/run 边界切换」才可实施；否则 L1 守住的 96.7% 折扣直接归零。

### V6【预热与 best-effort】前 1-2 轮无历史命中 + 构建延迟

- 「共同前缀检测」需要 ≥2 条请求才持久化单元（官方例 2：A+B、A+C 后第三条 A+D 才命中 A）→ 每个 run 的前 1-2 轮历史无命中（乐观第 2 轮、保守第 3 轮起）。冷启动成本 ≈ 2 轮 × 当时历史长度的 miss 价；早期历史短（~12k），约 $0.02/run，可忽略。
- 「缓存构建需数秒」：相邻两步间隔若小于构建时间（无工具快循环、重试风暴），上一轮的新单元未就绪 → 该轮历史 miss。agent loop 有模型生成（≥10s）+ 工具执行垫底，通常被吸收；风险集中在连续纯文本步。
- best-effort + 偶发驱逐：长期命中率是「主体命中、非 100%」，监控以 3 轮均值判定（调研报告已述）。

### V7【group 多参与者】跨 agent 零共享；跨 run 只有部分共享

- 不同 agent = 不同 soul/静态 prompt 字节流 → token 0 处即分叉；工具集通常也不同 → **跨 agent 连 S+Tools 都不共享**。group 场景的缓存收益完全在「每个 run 内部」。
- 同 agent 多 run 共享 thread：共享前缀延伸到「各自注入的 per-run 消息」（current_run directive、resume 输入）之前的共享 thread 历史 → 有部分跨 run 复用，但每个 run 仍付 1-2 轮预热；各自动态块（含 current_run/ledger/摘要）在尾部，**不影响共享前缀**——这正是「动态块放最后」在 group 场景的额外收益。
- 交错执行（多 run 轮流 step）无害：单元按内容持久化、存活数小时-数天，交错只是让每个 run 的 miss 尾巴按「距上次访问的间隔」增长（每次访问 miss 2Δ 而非 Δ）。

### V8【failover】切 provider 不毁缓存；换 model id = 冷启动

- DeepSeek 缓存是内容匹配的磁盘缓存（存活数小时-数天）：中途 failover 到别的 provider 跑几轮再切回，DeepSeek 的单元仍在，不失效。但对方 provider 侧有自己的缓存，首 2 轮全价；若 failover 是「每轮轮询/随机」，双方都退化为「隔轮访问、miss 尾巴翻倍」。
- **换 model id（同 provider）= 冷启动**：KV cache 按模型隔离，不同模型 token 化/模板不同。结论：模型 id 按 run 固定；切换 = 接受一次全 miss + 重新预热。
- 附带说明：重排后 Anthropic 路径比 DeepSeek 更稳——现有「最后一个 user 消息」断点（`client.py:2025-2039`）恰好落在动态块前，断点前缀 = system+历史；DeepSeek 则靠「共同前缀检测 + 固定间隔切块」双机制兜底。

### V9【口径】11,648 的组成与动态块大小需要实测确认

`11,648 ≠ 1,992(static) + 9,509(tools) = 11,501`，差 147 tokens；方案文档 §1 表格各分项之和（11,845）也与 11,648 对不上，说明表格分项与现网实测取自不同快照/agent。审计 §4 的收益估算按「11,648 = S+Tools」口径进行，落地验证时需用 `[Token Cache]` 日志逐项核对静态/工具/动态/历史四段 token 数，否则收益归因会失真。

## 2. 修正后的严格推演（token 级）

### 2.1 记号与前提

- `S` = system 静态字节流（现网 ≈2k）；`T` = tools schema 字节流（≈9.5k，恒稳定，前提 L1 确定性排序 + V5 不触发）。
- `U_i` = 第 i 轮的用户输入消息；`A_i` = 第 i 轮 assistant 回复（含 tool_calls）；`X_i` = 第 i 轮 tool 结果（一条或多条）。
- `H_i` = 截至第 i 轮的历史：`H_0 = ∅`，`H_i = H_{i-1} + U_i + A_i + X_i`（严格 append）。
- `D_i` = 第 i 轮动态块（dynamic_prompt + runtime JSON + runtime_instruction），每轮变化。
- `Δ = |A_i| + |X_i|` ≈ 现网实测 1k/轮。
- **前提**：DeepSeek 服务端把 tools 置于 messages 之前的 token 流中（见 §3.3 证据），重排后请求序列化为：

```
RQ_i = S + T + H_{i-1} + U_i + D_i
```

### 2.2 现状顺序为何恒 miss（对照实测，验证模型）

现状 `RQ_i = S + T + D_i + H_{i-1} + U_i`。`D_i ≠ D_{i+1}`（Current Time 每轮变）→ 任意两条请求的共同前缀 = `S + T`（分叉点在第 2 个消息的开头）。共同前缀检测持久化 `S+T`（11.6k），其后 `D_i + 历史` 永远位于任何前缀单元之外 → 全 miss。**与实测「命中恒 11,648、历史 33k 全 miss、input 每轮 +1k」逐项吻合**，模型可信。

### 2.3 重排后逐轮推演（第 N 轮 vs 第 N+1 轮）

**冷启动**：
- `RQ_1`：全部 miss（无任何可匹配单元）。请求边界持久化产生两个单元（用户输入结束位置 = `S+T+U_1+D_1` 全量；模型输出结束位置 = 全量+输出）；若输入够长另按固定间隔 I 切块。
- `RQ_2`：若共同前缀检测「随请求到达即时执行」（对比存量单元后先持久化再判命中），`CP(RQ_1, RQ_2) = S+T+U_1` 被持久化并即时命中，miss = `A_1+X_1+U_2+D_2`；若检测滞后一轮，`RQ_2` 只能靠 `RQ_1` 的间隔切块（早期输入短、未切块）→ 最坏全 miss。**即「第 2-3 轮起」的说法成立：乐观第 2 轮、保守第 3 轮。**

**稳态（第 N 轮 `RQ_N` vs 第 N+1 轮 `RQ_{N+1}`）**：

```
RQ_N   = S + T + H_{N-2} + U_{N-1} + D_{N-1}
RQ_{N+1} = S + T + H_{N-2} + U_{N-1} + A_{N-1} + X_{N-1} + U_N + D_N
           └────────── 共同前缀 CP = S + T + H_{N-2} + U_{N-1} ──────────┘
```

分叉点在 `U_{N-1}` 之后：`RQ_N` 这里是 `D_{N-1}`，`RQ_{N+1}` 这里是 `A_{N-1}`。推演分三种子模型：

1. **乐观（到达即时检测）**：`RQ_{N+1}` 到达时，系统把它与 `RQ_N` 的存量单元比对，持久化 `CP` 后即命中。`RQ_{N+1}` hit = `S+T+H_{N-2}+U_{N-1}`（≈43.6k），**miss = `A_{N-1}+X_{N-1}+U_N+D_N` = 上一轮的 Δ（≈1k）+ 本轮动态块（≈0.5k）**。这正是方案预期的「每轮 miss 仅剩新增消息 + 动态块」——注意精确表述：miss 的是**上一轮**追加的 assistant+tool（在本轮请求里已是历史），加本轮新输入和动态块，而非「本轮新增的 assistant」。
2. **保守（检测滞后一轮）**：`RQ_{N+1}` 只能命中更早的单元 `S+T+H_{N-3}+U_{N-2}`，miss 扩大到 2Δ + D（≈2.5k）。
3. **中间（间隔切块兜底）**：`RQ_N` 的输入是 `RQ_{N+1}` 的前缀、直到分叉点 `|S+T+H_{N-2}+U_{N-1}|` 为止。`RQ_N` 的间隔切块单元（边界取 I 的整数倍）中，最后一个 ≤ 分叉点的块可被 `RQ_{N+1}` 命中 → **即使共同前缀检测完全滞后，历史仍能命中到「分叉点前最近切块边界」为止，缺口 ≤ I**（I 官方未公布，若为 4-8k 则缺口最多几 k）。这是方案对 best-effort 的天然鲁棒性来源：两条独立机制（共同前缀单元 + 上一请求的切块）都覆盖历史主体。

**结论（修正后）**：重排后稳态 miss ≈ `Δ + |D|`（乐观）至 `2Δ + |D|`（保守），即 **~1.5k-2.5k/轮**，其余 ~43-44k 命中；命中主体不依赖单一机制。

### 2.4 动态块内部结构（审核任务 2）：验证边界

`D_i` 内的 Current Time 每轮变——**不影响其前的历史前缀，前提成立**。理由：前缀匹配只看「从 token 0 起到分叉点」的字节流，`D_i` 是序列最后一段，其内部任意变化只影响「`D_i` 起始位置之后」的匹配，而之后没有内容。两个边界条件必须满足：

1. `D_i` 之前不得有任何动态残留：V2 的两条 system 路径（runtime_instruction、确认态文案）必须清零/移出；`D_i` 必须是消息序列最后一条（V3）。
2. `D_i` 自身每轮全 miss（≈344 + runtime JSON ≈ 0.3-1k）——这是方案的固定成本，已计入 §4。runtime JSON 序列化已 `sort_keys=True`（`model_step_service.py:617-622`），确定性良好（对命中无影响，但利于测试/审计）。

### 2.5 tools 的位置（审核任务 3）

- 请求体层面：`payload` 中 `messages` 在 `tools` 之前（`client.py:622-641`），但 **JSON 键序不决定 token 流**；决定命中的是服务端拼装顺序。
- **现网实测即证据**：动态 user 消息位于 messages[1] 且每轮变，而命中恒为 11,648（S+Tools）→ 若 tools 在 messages 之后序列化，tools 必在分叉点之后、不可能恒命中。唯一自洽解释：**DeepSeek 服务端把 tools 置于对话之前**（OpenAI 兼容服务将工具定义前置注入是通行做法）。
- 推论 1：**tools 属于缓存前缀的一部分**；重排 messages 不改变 tools 在 token 流中的位置（仍在 messages 之前），S+Tools 前缀不受重排影响，重排纯粹把「历史」从分叉点之后移入命中区。
- 推论 2：tools 字节稳定性是前缀命中的必要条件（L1 确定性排序已保障）；且因所有单元从 token 0 起算，**tools 任何变动会使包括历史单元在内的全部单元失效**（V5）。

### 2.6 fallback 与 group（审核任务 4）

见 V7/V8。一句话：缓存按「内容 + 模型」隔离、存活小时-天级；跨 provider 切换不销毁 DeepSeek 缓存但对方侧冷启动；跨 agent 零共享；同 agent 共享 thread 有部分共享；动态块每 run 不同但因在尾部而无害。

### 2.7 变体对比（审核任务 6）

| 变体 | 序列 | 共同前缀（RQ_N ∩ RQ_{N+1}） | 结论 |
|---|---|---|---|
| **A（方案）动态块在新增消息之后** | `H_{N-1} + U_N + D_N` | `S+T+H_{N-2}+U_{N-1}` | **最优**。前缀覆盖到当前输入，`U_N` 下一轮即成为命中区 |
| B 动态块在新增消息之前 | `H_{N-1} + D_N + U_N` | `S+T+H_{N-2}`（分叉点在 `D_N` vs `U_{N-1}` 处提前） | **严格更差**：持久化前缀短一条消息（`U_{N-1}` 首轮 miss），miss 多出 `U_{N-1}`；且运行时快照插在历史与当前输入之间，语义更差 |
| C 动态块合并进 `U_N` | `H_{N-1} + (U_N‖D_N)` | 同 A，但 **禁止**：合并后的消息下一轮从历史回放时不含 `D_N`（或含过期 `D`）→ 该消息字节流跨轮不一致 → 前缀断裂 | 否决 |
| D 稳定段从动态块上提 | 把 session_context_snapshot 等上提到历史之前 | 仅当该段在整个 run 内字节不变才可行；checkpoint 版本变化即全灭 | 否决（收益小、风险大，保持全动态入尾部最稳） |

**没有比 A 更优或等价的变体**；「动态块放最后」就是最优解。可做的加固只有：动态块构建一次、run 内重试复用（避免重试时 Current Time 变化导致重试请求连尾部都不命中）——微优化，非必需。

## 3. 收益重估（审核任务 5，修正后）

价格（DeepSeek off-peak）：命中 $0.022/M，miss $0.66/M（peak 翻倍，下述金额均 off-peak 口径）。

| 场景 | hit/轮 | miss/轮 | 每轮成本 | 备注 |
