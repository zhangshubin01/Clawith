> 测量对象：Android 工程师06（agent `b1a73489`，deepseek-v4-flash）

## 一、结论摘要

1. **静态系统提示并不大**：实测 7,444 字符 ≈ 1,974 token（含 soul、基础提示、能力策略、Skills 目录）。
2. **基础前缀 ≈ 26.6–27.6K 真实 token，构成 = 工具 schema ~6-8K + 系统 2K + 线程历史 ~4-5K + 公共前缀匹配余量**（修正：此前的「跨 run 历史 24.5K」归因有误，见 §二.1）。
3. **工具结果是线程体积的绝对主导**：run 结束态线程 27 条消息，tool 消息 14 条共 21,672 字符（≈5.7K token），单条 read_file 结果 3,000–4,700 字符。
4. **每步仍有 0.4–5.3K token 的未命中输入**：= 动态块（每步全量重建、在 cache 边界外）+ 终控消息 + 新增工具结果；早期步 <1K，随动态块增长与工具结果变大而上升。
5. **压缩触发符合设计但周期太短**：0.8×108K≈86.7K 估算水位，36 步任务触发 2 次（step 17、step 24），每次付 18-30s 摘要调用 + 后续 2-3 步 30-67s 的缓存重建。

### 1. 基础前缀（每 run 第 0 步即背负，provider 实测 cache_read ≈ 26.6–27.6K token）

> 2026-08-26 修正：此前把 ~24.5K 归因为「跨 run 线程历史」有误。后续实测：工具 schema 34 工具 = 5,961 token（DB 实测）、静态系统提示 1,974、run 起始消息链仅 4 条（线程历史 ~4-5K）。基础前缀 ≈ 工具 schema ~6-8K（运行时含内置文件工具）+ 系统 2K + 线程历史 4-5K + 其余 ~10-14K（疑为 DeepSeek 公共前缀 unit 与更早请求匹配，待 provider 侧确证）。

## 三、瘦身方案（最终裁决见 `20260826-context-slimming-plan-review.md`）

> 本节为原始提案（保留供对照）；三源证据审查后的修正版裁决与执行顺序在审查文档 §6：
> **P0 = ②工具结果截断（先 A/B）+ ③动态块拆分**；P1 = ①跨 run 治理（降级为中杠杆，落地仓库 L1）+ ⑤工具描述精简 + ⑥压缩模型分级；P2 = ④验证门微调 + ⑦阈值 A/B。

1. ~~【最大】跨 run 历史治理~~ → **降级**：基础前缀中跨 run 历史实测仅 ~4-5K（非 24.5K）。
2. **【P0】工具结果裁剪**：read_file 等结果截断（4.7K→2K 字符量级）+ 恢复路径（path+offset/limit 指引）+ 错误信息优先 + 只截旧结果；先 A/B。
3. **【P0】动态块拆分**：每步稳定部分（thread_running_summary、session_context_snapshot）移入 cache 边界内，仅真正每步变化的部分留在块内 → 每步未命中 2-5.3K → ~1K。
4. ~~【中】验证门降频~~ → **撤销**：验证门已只在终止步执行一次；剩余仅输入瘦身（P2）。
5. **【小】不动的**：压缩水位 0.8 设计正确；缓存机制本身健康（步间命中 90%+）。
