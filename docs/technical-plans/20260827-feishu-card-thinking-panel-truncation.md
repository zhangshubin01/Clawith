# 飞书卡片思考面板终版截断（2026-08-27）

## 背景与证据

飞书卡片「💭 思考过程」面板的原文 = DeepSeek `reasoning_content` 流式增量逐轮累积
（链路：`client.py` stream → `model_step_service._card_on_thinking` →
`CardStreamBridge.push_thinking`），**无界增长**。reasoning 回放协议决定了历史里
reasoning 占大头（实测 70–93%），且随轮次单调增长。

真实 run 6047ba80（2026-08-27 01:48–01:54，「@MG2 Android工程师 现在有什么待办的？」，
deepseek-v4-flash）实测：10 个模型轮次，思考总量 **79,890 字符 / 793 行**，终版卡片
思考载荷 81,485 字符（quote 后），而正文仅 1,004 字符。

风险：正文在 `_build_terminal_card` 有 28,000 截断，思考却零上限；长 run（平台上限
50 轮）可到几十万字符，打爆 CardKit 载荷上限时 `finalize()` 的 `update_cardkit_card`
失败，**整张卡片（含正文）降级为纯文本**。

## 决策

终版卡片思考面板改为**保留尾部**，上限 **8,000 字符**，超限时内容顶部加一行
`> ⚠️ 思考内容过长，仅展示最后一段`。

- 为什么是尾部：思考按轮次顺序追加，尾部 = 最新几轮，正是用户展开面板时最想看的；
  与实时面板 `[-2000:]` 尾窗的展示思路一致（实时面板是滚动窗 2000，终版保留尾段 8000，
  两者阈值不同：实时窗追求跟手、终版保留更多上下文）。
- 为什么是 8,000：80K 的实测 run 中单轮 reasoning 多在 2K–18K，8K 能保住最近一轮完整
  思考 + 部分上一轮；同时终版卡片总载荷（思考+正文 28K+工具）落在 CardKit 安全区间。
  该值无严格数学依据，是按实测轮次长度的工程取值。
- 行边界裁剪：丢弃切点处的首行碎片，避免首行拦腰截断。
  **退化场景**：单条思考增量本身是无换行、>8,000 的超长行时，8,000 上限优先于行边界
  （两者物理冲突，无法两全）。
- 折叠面板不改变本决策：CardKit JSON 无论折叠与否都携带全文，载荷风险与折叠无关。
  默认折叠（`expanded: False`）只影响展示，不影响载荷。

- 全量基线：3032 passed（2026-08-27）。
